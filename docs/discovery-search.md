# 関係探索の候補を改善する

従来の選択した問いからの統合探索は、主に先頭24個の二文字単位の語と分類でSQL候補を絞り、最大30件だけAIに渡していた。語彙が異なる反例・因果・異分野の資料は、AIが見る前に除外される可能性があった。リファクタの索引再利用は速度を改善したが、この候補の見落としは解決していなかった。

## 明示的な探索で行う処理

1. 選択した問いの主題・内容から、AIが検索語を生成する。直接の言い換え、原因、結果、反例、異分野の類似構造を最大5方向、各1〜4語に制限する。
2. 各方向の語で、全期間の現行・表示対象の問いと抽出済み記録をSQL検索する。各方向の上限は問い12件、記録12件。SQLはパラメータ化し、AIにSQLや任意の操作を実行させない。
3. 既存の問いに所属する材料も分類や語の一致とは別に拾い、従来の候補を最大5枠保持し、拡張検索を各方向から順番に取り込む。合計最大10件、同一本文は重複排除。分類が同じ大量の記録だけで枠を使い切らない。
4. AIが実際の候補本文を比較する。検索方向は仮説として扱い、共通する機構・成立条件と重要な違いを具体的な理由にする。「同じ話題」だけでは有用としない。因果を本文以上に断定せず、類推は仮説とする。対立と同一化を混同しない。
5. 現行版を再確認し、結果を保存する。統合やリンクの採用は従来通り別の操作で行う。

探索1回のAI呼び出しは、検索計画と関係判定の2回となる。保存やページ表示から自動実行しない。探索のIDを最初に確保し、同じ操作の再送・保存結果の再表示は追加AIを呼ばない。失敗した探索も自動で再実行しない。

画像などの記録も、元の空本文より抽出本文を検索する。検索用の主題・内容から語を取り、問いのID等のJSONメタデータを先頭語として拾わない。検索計画と方向ごとのヒット件数は保存した探索結果に残す。

## 検証と限界

合成データでは、似た語の記録80件で従来候補を埋めても、「推論の効率化」に対して「燃費向上で走行距離が増える」という古い異分野の資料を拡張語から拾い、関係判定へ渡せることを確認する。非表示資料、重複、候補枠、再送、無効な検索計画も検証する。

これは候補回収の回帰検証で、実モデルの関係判定精度を測る評価ではない。AIが適切な語を生成しない場合や、各方向の上限に埋もれる資料は引き続き見落とす。全件の関係を保証する仕組みではない。全体から複数の統合案を提案するホームの探索と、親子・対立を提案する関係探索は、今回の変更対象とは分ける。

## 将来の意味の層

タグに加えて、概念の定義・別名・対象・期間・成立条件・主張・根拠・関係を持たせると、語彙が違う資料を共通の概念や機構から探せる。似た文章を拾うベクトル検索だけでは、仮説の方向、対立、同一条件での比較まで表現できない。

Bookでは原文、AIの仮説、ユーザーが採用した関係を区別して扱う設計が適する。たとえば「単価低下→利用増→総量増」は、確定した因果ではなく条件と出典を持つ仮説として扱う。今回、この意味の層や新しいタグ体系は追加しない。
